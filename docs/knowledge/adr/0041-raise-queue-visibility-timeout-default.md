# ADR 0041: Raise Azure Storage Queue default visibility timeout to 900s

## Status

Accepted

> Current sprite-workflow operations belong to
> [`.specify/specs/sprite-generation-pipeline.md`](../../../.specify/specs/sprite-generation-pipeline.md).
> This ADR is kept as the rationale for why the default moved to 900 seconds.

## Date

2026-07-02

## Estimated Complexity

🍎 x 2 — a one-constant default change with a cost/robustness tradeoff, plus
threading the override through the connection-string factory and unit coverage.
No new lab or ECS system.

## Context

Sprite art is generated by an in-process worker (`scripts/sprites/worker.ts`,
ADR 0018 "Sidecar Owns an In-Process Sprite-Generation Worker") that pops one
`AssetRequest` at a time from an Azure Storage Queue
(`scripts/sprites/queue/azure-queue.ts`). Each request drives one **16-cell**
sprite-sheet generation via `gpt-image-1`.

Azure Storage Queues are at-least-once: `receiveMessages` hides a message for
`visibilityTimeout` seconds; the worker must `ack()` (delete the message by
`messageId` + `popReceipt`) before that window closes, or the message resurfaces
and is redelivered. The queue was constructed with
`DEFAULT_VISIBILITY_TIMEOUT = 300` (5 minutes).

Live observation of the one-command sidecar (`npm run sprites:gallery`, shipped
in PR #659) showed the 300s default is **marginal**:

- A 16-cell `gpt-image-1` generation runs **~4 minutes typically** and **up to
  ~6 minutes** for slower briefs.
- When a run exceeds 300s, the message becomes visible again **mid-run**. The
  original pop receipt goes stale, so the worker's success-path ack
  (`deleteMessage(messageId, popReceipt)`) fails with the Azure error
  **"The specified message does not exist."**
- The brief therefore never acks, `worker.processed` stays `0`, and the same
  request is redelivered and **regenerated** — burning `gpt-image-1` API spend
  for no forward progress.

A typical ~4-minute (240s) run barely fits the 300s window (~60s margin); a slow
~6-minute (360s) run blows past it. This is downstream of, and distinct from,
the ADR 0037 poison-message fix (`MAX_DEQUEUE_ATTEMPTS = 3` + at-most-once
acking), which already **bounds** any residual failures — so the pipeline is
safe today, but it is **unproductive** for slow briefs and silently wastes money
by regenerating work that actually succeeded.

The env override (`AZURE_STORAGE_QUEUE_VISIBILITY_TIMEOUT`, read in
`scripts/sprites/queue/index.ts`) was already validated live: setting it to
`900` made the backlog productive — `worker.processed` climbed `0 → 1 → 2` with
`failed = 0`, zero "message does not exist" ack failures, and zero bad grids.
Requiring a manual env override for the documented one-command start is the
problem this ADR removes.

A secondary defect surfaced during plan review: `AzureStorageQueue.fromConnectionString`
always passed `DEFAULT_VISIBILITY_TIMEOUT` and ignored the parsed override, so
when `AZURE_STORAGE_CONNECTION_STRING` was set the
`AZURE_STORAGE_QUEUE_VISIBILITY_TIMEOUT` env var was silently dropped — the
override was only honored on the account/key path.

## Decision

1. **Raise the code default** `DEFAULT_VISIBILITY_TIMEOUT` from `300` to `900`
   (15 minutes) in `scripts/sprites/queue/azure-queue.ts`. 900s gives robust
   margin: ~2.5× over a typical ~4-minute run and ~1.5× over a slow ~6-minute
   run, so a generation finishes and acks before the message can resurface.
2. **Honor the override on both construction paths.** Thread an optional
   `visibilityTimeout` parameter through `AzureStorageQueue.fromConnectionString`
   and pass the parsed `AZURE_STORAGE_QUEUE_VISIBILITY_TIMEOUT` value from
   `createAssetQueue` on the connection-string path, so the env override and the
   per-call option are genuinely intact regardless of how the queue is built.
3. **Keep the override knob.** The `AZURE_STORAGE_QUEUE_VISIBILITY_TIMEOUT` env
   var and the per-call `visibilityTimeout` option remain the escape hatch for
   environments where `gpt-image-1` latency differs; only the fallback default
   moved.

## Consequences

### Positive

- The one-command sidecar start works reliably out of the box — no manual env
  override needed for slow briefs.
- Slow (~6-minute) generations finish and ack inside the window, eliminating the
  false "message does not exist" ack failures and the wasteful regeneration of
  already-successful work.
- The env override and per-call option now behave identically on the account/key
  and connection-string paths, removing a latent silent-drop footgun.

### Negative

- For a **genuine** stall or transient mid-run failure where the worker does not
  ack, redelivery latency grows from ~5 minutes to ~15 minutes. This is the
  intended tradeoff: a longer window is exactly what lets a legitimately slow run
  finish. The blast radius is bounded — `MAX_DEQUEUE_ATTEMPTS = 3` still caps
  total retries (worst case ~3 × 15 min before a permanent drop), and a crashed
  worker is restarted long before the timeout elapses.

### Risks

- `900` is an empirical heuristic tuned to observed `gpt-image-1` timing. If
  model latency grows materially, a slow brief could again approach the window;
  mitigation is the retained env/option override and the named constant with
  inline rationale. Azure's maximum visibility timeout is 7 days, so 900s is well
  within limits and leaves ample headroom to raise further if needed.

## Alternatives Considered

- **Keep 300s and require the manual `AZURE_STORAGE_QUEUE_VISIBILITY_TIMEOUT=900`
  override.** Rejected: it defeats the point of the one-command start, and the
  default path silently wastes `gpt-image-1` spend regenerating successful runs.
- **Raise to a smaller value (e.g. 600s).** Rejected: only ~1× margin over a slow
  ~6-minute run — still marginal. 900s gives a comfortable buffer without being
  excessive.
- **Only narrow the docs/claim instead of fixing `fromConnectionString`.**
  Rejected: it would knowingly leave the env override silently broken on the
  connection-string path in code this change already touches and documents.
