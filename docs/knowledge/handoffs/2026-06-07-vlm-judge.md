# Session Handoff: VLM judge for sprite pipeline (spec §F4)

## Date

2026-06-07

## What Was Done

Implemented the VLM judge — the second quality gate after the deterministic
sensors, per spec `§F4` and plan build 2. Three evaluators in a single vision
call per variant: `style_match`, `brief_match`, `readability`. Each scores
1–5; anything `< 3` on any evaluator auto-rejects the variant. Local-only,
opt-in per brief.

### New files

- `scripts/sprites/provider/vision-types.ts` — `VisionProvider` interface,
  typed `VisionProviderError` (auth | rate-limit | network | malformed |
  provider-error), labelled `VisionImageInput`.
- `scripts/sprites/provider/azure-vision.ts` — Azure chat-completions adapter
  for vision. Injectable `fetch` for tests, no retry (caller owns), permissive
  JSON parser, base64 `data:` URLs with `detail: 'high'`, temperature
  defaults to 0.
- `scripts/sprites/judge.ts` — orchestrator. Refuses to run when `process.env.CI`
  is set (Constitutional §3, with an ADR escape hatch). Single vision call per
  variant. Zod-validates the response. Writes `processed/NN.judge.json`
  alongside the existing sensor scorecard (does not overwrite it).
- `tests/unit/sprites/azure-vision.test.ts` — 14 tests.
- `tests/unit/sprites/judge.test.ts` — 15 tests (CI refusal, happy path,
  threshold edges, malformed, error propagation, single-call discipline,
  artifact write/skip).
- `tests/integration/judge-pipeline.test.ts` — 4 end-to-end tests through
  `generateOne` with mocked image + vision providers.

## What's Next

1. **Try the judge on real briefs.** Flip `judge.enabled: true` on
   `briefs/weapons/iron-sword.yaml` (or `katana.yaml`) and run
   `npm run sprites:one -- briefs/weapons/iron-sword.yaml`. Measure real
   per-variant token cost; compare judge verdicts to your eyeball verdicts
   on the same variants. After 3–4 briefs' worth of data, decide whether to
   default `judge.enabled: true` on the weapon sprite type.
2. **Cost ceiling per run.** `maxVariants` already caps judging per
   `generate-one` call, but there's no per-batch (i.e. across many briefs)
   ceiling. A `SPRITES_JUDGE_BUDGET_USD` env var that the orchestrator can
   watch (using the `usage` field already surfaced on `EvaluateResponse`)
   would prevent unattended batches from accidentally running up a bill.
3. **Judge prompt iteration.** The current evaluator definitions in
   `judge.ts` are an honest first pass and they read fine, but the only
   way to know if the rubric matches the failure modes humans care about
   is to run it on real data and audit the rationales. Expect to tune the
   `style_match` rubric in particular — it's the vaguest of the three.
4. **Cache by prompt+image hash.** Identical (sheet, variant, references)
   tuples will produce identical vision calls on re-runs. Hashing the
   request and caching the response under `runs/.judge-cache/` would make
   re-runs of the same brief free.

## Key Decisions Made

- **One vision call per variant** for all three evaluators (single
  structured-JSON response) — cost discipline. Fanning out to three calls
  would 3× the per-variant bill without a clear quality gain.
- **Sequential judging, not parallel** — predictable rate-limit headroom on
  Azure, easier per-variant attribution in logs. Wall-clock isn't a problem
  for one-shot brief runs; if it ever becomes one for batch runs, a small
  `Promise.all` chunker is a 5-minute change.
- **Two-pass orchestrator** (write all sensor artifacts first, then judge
  the sensor-passing subset) — so a judge failure can't corrupt sensor
  artifacts that are already known-good. Also lets `maxVariants` cap the
  judge by ranking on sensor score first.
- **`combinedPassed = sensors.passed && (judgeDisabled || judge.passed)`** is
  a separate field from `passed` (sensor-only) so existing consumers of
  `RunSummaryEntry.passed` keep their old semantics. `chosen` and CLI
  `--pick` switched to `combinedPassed`.
- **CI refusal is on `env.CI !== undefined`** (any value, not just truthy),
  matching what every CI provider sets. Injectable `env` for tests.
- **`maxVariants: 16` default** matches the largest brief grid we ship
  (4×4) so the default behavior on enable is "judge every sensor-passing
  variant"; smaller budgets are opt-in.
- **Judge scorecards live in `processed/NN.judge.json`** as a separate
  sidecar, not merged into the sensor scorecard. The two gates have
  different shapes, different failure semantics, and different upgrade
  cadences; merging would create a coupling we don't want.
