# Merge-train work stoppage: shared owner-PAT rate-limit exhaustion

Date: 2026-07-30
Apples: 🍎🍎 (tooling/automation incident restore)

## Systems touched

ci-automation, merge-train, ci-recovery

## Symptom

Nothing merged to `main` for ~7 hours (last merge 09:42Z, incident opened 16:18Z).
Every open PR sat at `BEHIND` or `BLOCKED`, the merge train reported
`Merge train is empty` while its own liveness check listed admission-eligible PRs,
and the `CI Conflict Coordinator` reconcile job exited 1.

## Root cause

`CRAWLER_CI_PAT` is a classic user PAT. GitHub applies a **user-level** 5,000
req/hour core budget shared across all of that user's tokens, and returns
`403 API rate limit exceeded for user ID <id>` on every REST call once it trips —
including calls made by other tokens belonging to the same user.

`ci-recovery.yml` is the repo's highest-volume REST consumer: it is dispatched
per PR, per CI completion, per review-comment event, and by the 10-minute
liveness sweep, and `reconcile.mjs` routed **all** of its reads through
`CRAWLER_CI_PAT` (`readToken = pat || GITHUB_TOKEN`). That exhausted the shared
budget, which then 403'd every other owner-scoped automation.

The resulting deadlock was self-reinforcing:

1. CI recovery 403s → review threads never reconciled and the `merge-train`
   admission label is never applied (CI recovery is what applies it).
2. No PR carries `merge-train` → the train reconciles to "empty" and merges
   nothing.
3. Nothing merges → the open-PR backlog grows → more PRs to reconcile → the
   budget is re-exhausted within minutes of every hourly reset.

Aggravating factor: the `Merge Train` reconcile triggered by the `push` to main
was `cancelled` by its `queue: single` concurrency group on the last two merges
(08:19Z, 09:42Z), so the train never got a post-merge reconcile either.

## Fix landed (direct to `main`, 9d30add61 — authorized work-stoppage bypass)

`reconcile.mjs` reads now prefer `CI_RECOVERY_READ_TOKEN`, a GitHub App
installation token generated by `ci-recovery.yml` (separate rate-limit bucket),
falling back to the PAT then `GITHUB_TOKEN` so local runs and tests are
unchanged. Two call sites deliberately stay on the PAT because they depend on
PAT _identity_, not just authorization:

- `workflow_dispatch` — App-attributed dispatches can park in `action_required`.
- `update-branch` — the push must emit a normal push event to re-trigger required
  CI (`GITHUB_TOKEN` is recursion-suppressed).

`node --test .github/scripts/ci-recovery/reconcile.test.mjs`: 159 tests, 0 fail.

## Manual restore actions

- Resolved 7 review threads on #2382/#2378/#2375 that already carried a trusted
  `✅ Addressed in <sha>` / `✅ Not applicable:` reply. This is exactly the dead
  reconciler's deterministic contract, executed by hand via GraphQL (GraphQL has
  its own quota bucket and stayed healthy throughout — use it when REST is 403ing).
- Seeded the empty train by applying the `merge-train` label to #2375 and #2010,
  the two PRs the train's own liveness incident (#2383) certified as
  admission-eligible. Labeling also re-triggers Merge Train via
  `pull_request_target: [labeled]`, so no REST dispatch was needed.

## Observed result (real artifact, not a lab)

- `main` advanced from `00bdda09d` → `b3e965264` (#2010) → `abb949bc2` (#2375)
  within ~10 minutes, after 7 hours of zero merges.
- CI recovery then **auto-admitted #2363** to the train on its own (label applied
  by automation, not by hand), confirming the recovery loop is self-driving again.
- Copilot agents resumed work on #2378/#2373/#2369/#2368/#2365.
- Verified in the CI Recovery run log that `CI_RECOVERY_READ_TOKEN` is populated
  and the App token is issued and revoked per run.

## Follow-ups (not done here)

- The user-level budget is still tighter than the automation's peak demand. Other
  `CRAWLER_CI_PAT` consumers (`action-required-retrigger`, `ci-recovery-incidents`,
  `pr-ready-reviewer-guard`, `sprite-queue-reconciler`) should move their reads to
  the App token the same way.
- One `pull_request_review_comment:created` event dispatches one full CI Recovery
  run. A batch of reviewer comments produces a burst of runs that all exit
  `skip duplicate-fingerprint`. Debouncing that dispatch is the biggest remaining
  volume reduction.
- No deterministic guard exists for "merge train empty while eligible PRs are
  stalled" beyond the incident issue. Promoting that to a check that also reports
  remaining rate-limit budget would have caught this in minutes rather than hours.
- The local workstation had 698 leaked `copilot` processes holding ~44 GB RSS,
  accumulating at ~56/hour. Unrelated to the API budget but worth reaping.
